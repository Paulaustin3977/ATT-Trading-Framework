## 1. Executive Summary

This plan defines how diagnostic-only RiskEngine v1.0.0-draft will be added to ATE v2.2 as a new release file with diagnostic dashboard and Research Mode outputs only.

The implementation must NOT change existing ATE v2.1 behaviour except for additive diagnostic visibility. RiskEngine may read `volScore`, `volShockFlag`, `confidenceScore`, `trendScore`, `structureScore`, `momentumScore`, ATR, and swing values for its own diagnostic classification. It must NOT influence any other engine, decision, trade, alert, sizing, or stop pathway in ATE v2.2.

After Pine implementation, the EDR-001 canonical verifier (`python tools/scripts/verify_ate.py`) is the implementation gate. The verifier's pass means the spec contract holds. It does NOT replace RDR-001 validation, which is a separate empirical study that must follow ATE v2.2 release candidate preparation.

---

## 2. Scope

ATE v2.2 RiskEngine shall:

- Implement the four-component diagnostic scoring from the approved RiskEngine v1.0 Draft (`volatility 35 / extension 30 / structure 20 / conflict 15`).
- Publish the six Engine Output Contract fields: `RiskScore`, `RiskState`, `RiskDirection`, `RiskReason`, `RiskEngineVersion`, plus named diagnostic variables.
- Display as part of DashboardEngine.
- Record as part of Research Mode.
- Use bar-close-only logic.
- Stay diagnostic-only.

---

## 3. Non-Scope

ATE v2.2 RiskEngine shall NOT:

- Modify `pine/releases/ATE_v2.1.pine`.
- Modify `confidenceScore`, `marketState`, `TrendScore`, `StructureScore`, `MomentumScore`, or any VolatilityEngine output (`volScore`, `volShockFlag`, `volState`, `volDirection`, etc.).
- RiskEngine must not affect confidenceScore.
- RiskEngine must not affect marketState.
- RiskEngine must not affect trendScore.
- RiskEngine must not affect structureScore.
- RiskEngine must not affect momentumScore.
- RiskEngine must not affect VolatilityEngine.
- RiskEngine must not affect DecisionEngine.
- RiskEngine must not affect any entry/exit logic.
- RiskEngine must not affect position sizing.
- RiskEngine must not affect stop logic.
- RiskEngine must not create alerts.
- RiskEngine must not output bullish or bearish direction.
- RiskEngine must not modify ATE v2.1 release file.
- ATE v2.2 must be a new release file only.
- Generate buy or sell signals.
- Produce bullish or bearish direction or state values.
- Use reserved language: `safe`, `unsafe`, `suitable`, `unsuitable`, `approved`, `blocked`, `tradeable`, `untradeable`.
- Reach into any other engine's internals.
- Introduce position, account, broker, or paper-trading integration.
- Modify the active ATE release file (ATE v2.1) or any other engine specification.

## 5. Pine Implementation Approach

Implementation must be additive, isolated, and explicitly reversible to the ATE v2.1 baseline.

Steps:

1. Copy `pine/releases/ATE_v2.1.pine` to `pine/development/ATE_Current.pine` only after reading the ATE v2.1 file. Do not edit ATE v2.1.
2. Append the RiskEngine input group, function group, computation block, dashboard rows, and Research Mode outputs in clearly labelled sections.
3. Use prefix `riskScore`, `riskState`, `riskDirection`, `riskReason`, `riskEngineVersion`, and `riskDiag*` for each diagnostic variable. The prefix `risk*` (no `vol` or any other engine's prefix) avoids shadowing.
4. Add the EOC output publishing block at the end of the RiskEngine computation. Map each EOC field to a named Pine variable that is exactly equal to one of the spec-mandated names.
5. Extend `tools/scripts/verify_ate.py` so it can:
   - load `pine/releases/ATE_v2.2.pine`,
   - parse the RiskEngine output column declarations,
   - parse the seven inputs and their defaults,
   - assert the four-component cap table,
   - assert the diagnostic-only contract by scanning for reserved language and forbidden patterns.

Implementation must be verifiable end-to-end with no Pine code outside the new release file.

## 6. New RiskEngine Inputs

Seven diagnostic-only inputs, all to be declared as `input.*` with literal defaults:

| Pine input name | Default | Allowed range | Purpose |
|---|---:|---:|---|
| `riskVolElevatedScore` | 25 | 0–100 | volScore threshold above which volatility counts as risk. |
| `riskExtensionAtrLow` | 1.5 | 0.5–5.0 | Low-end ATR multiple for low-extension risk. |
| `riskExtensionAtrHigh` | 3.0 | 1.0–10.0 | High-end ATR multiple for high-extension risk. |
| `riskSwingAtr` | 2.0 | 0.5–6.0 | ATR multiple where a swing distance becomes risky. |
| `riskConfidenceRiskHigh` | 80 | 50–100 | Confidence threshold above which extreme confidence becomes a risk signal. |
| `riskConfidenceRiskLow` | 20 | 0–50 | Confidence threshold below which extreme low confidence becomes a risk signal. |
| `riskSmoothingLength` | 3 | 1–20 | Bars over which the risk score is smoothed. |

Pine v6 constraints:

- `maxval` and `minval` must be literal constants (not other inputs).
- Defaults must not be silent.

The seven inputs above exactly match the values in the approved RiskEngine Specification section 6.

## 7. New RiskEngine Variables

Required computed variables (per spec sections 5 and 7):

- `riskScore` — numeric 0..100 (smoothed risk total, clipped).
- `riskState` — enum `calm` / `normal` / `elevated` / `tense` / `extreme` / `unknown`.
- `riskDirection` — enum `none` / `elevated` / `conflict` / `stable` / `indeterminate`.
- `riskReason` — short deterministic text.
- `riskEngineVersion` — string `"1.0.0-draft"`.

Component-state and raw-component variables:

- `riskVolState`, `riskExtState`, `riskStructState`, `riskConflictState` — per-component state tags.
- `riskVolRaw`, `riskExtRaw`, `riskStructRaw`, `riskConflictRaw` — per-component raw contributions before smoothing.
- `riskTotalRaw` — sum of raw components.
- `riskSmoothedRaw` — `riskTotalRaw` averaged over `riskSmoothingLength` bars.

Diagnostic variables (named individually per spec section 5.3):

- `riskDiagVolScore`, `riskDiagVolShockFlag`
- `riskDiagExtBarRangeAtr`
- `riskDiagStructLastSwingAtr`
- `riskDiagConfidenceScore`, `riskDiagConflictCross`
- `riskDiagInsufficientData`

Naming constraint: every RiskEngine variable name begins with `risk` or `riskDiag`. The `risk*` prefix avoids shadowing across engines.

## 8. Engine Output Contract Mapping in Pine

| EOC field | Pine variable | Allowed values | Notes |
|---|---|---|---|
| `score` | `riskScore` | numeric 0..100 or `na` | Smoothed, clipped. |
| `state` | `riskState` | `calm` / `normal` / `elevated` / `tense` / `extreme` / `unknown` | Precedence `unknown > extreme > tense > elevated > normal > calm`. |

The verifier (see §12) must locate each variable by name and assert its presence, allowed value range, and that RiskEngine output block is the only place that publishes those names.

## 12. Verification Requirements

After Pine implementation:

1. Run the canonical verifier:
   ```
   python tools/scripts/verify_ate.py
   ```
   Exit code 0 with `passed == 270/270` (current count) plus any new ATE v2.2 contract checks. The verifier will require an update that loads `pine/releases/ATE_v2.2.pine` and includes RiskEngine contract assertions.

2. Required verifier rules for RiskEngine:
   - presence of `riskScore`, `riskState`, `riskDirection`, `riskReason`, `riskEngineVersion`, `riskDiag*` in the release file;
   - allowed values for `riskState` (`calm`, `normal`, `elevated`, `tense`, `extreme`, `unknown`);
   - allowed values for `riskDirection` (`none`, `elevated`, `conflict`, `stable`, `indeterminate`);
   - absence of `bullish` and `bearish` in the RiskEngine output block;
   - absence of reserved language in RiskEngine dashboard labels and Research Mode fields;
   - presence of the four-component cap table in the Pine release;
   - presence of the seven input defaults matching the approved values exactly;
   - presence of the version literal `1.0.0-draft`;
   - no `alertcondition()` or `alert()` text containing "risk" or "Risk" labels.

3. The verifier must fail (exit 1) on any violation. The verifier output remains `ad-hoc hermes-verify, NOT suite green`.

Passing the verifier does NOT replace RDR validation. The verifier only proves that the release file matches its approved contract; it does not prove empirical usefulness.

## 14. Hermes RDR Validation Requirements after Implementation

After Pine implementation passes the verifier, RDR-003 (`RDR-003-volatility-diagnostic-validation.md`, extending the RDR-002 / RDR-002W pattern) must be run by Hermes as a separate, empirical study. RDR-003 is not the verifier. RDR-003 must include:

- hypothesis that RiskEngine diagnostic states occur sensibly across ATE v2.2 universe;
- state frequency analysis per asset and per asset class;
- state duration statistics (min / median / mean / longest);
- transition analysis between the six states;
- component contribution breakdown per state;
- overlap with VolatilityEngine (target: low to medium; auto-correlated with volRisk);
- overlap with MomentumEngine (target: low);
- hidden directional bias check (no bullish/bearish leakage);
- explanation-from-diagnostics quality (can the dashboard rows explain each state?);
- negative findings capture;
- classification: `supported` / `weakly supported` / `inconclusive` / `falsified` / `operationally rejected`.

RDR-003 classification is independent of the verifier passing. The verifier only constrains correctness of contract; RDR-003 constrains empirical usefulness.

RDR-003 must be approved before RiskEngine can be considered for any future feed into DecisionEngine, ConfidenceEngine, or downstream consumer layers.

## 15. Risks and Mitigations

| Risk | Severity | Mitigation |
|---|---|---|
| RiskEngine accidentally affects other engines | High | RiskEngine reads only from already-published inputs (volScore, volShockFlag, confidenceScore, trendScore, structureScore, momentumScore, ATR, swing values). It does not write to any other engine's variables. Verifier scans the Pine source for the absence of writes. |
| Hidden strategy risk via wording | High | Reserved-language list is enforced at the verifier level. Dashboard labels must use `Risk` prefix plus diagnostic words only. |
| VolatilityEngine double-counting | Medium | Volatility contributes up to 35/100 (≤ 1/3 of max risk score). The verifier checks component cap table. |
| ConfidenceEngine feedback loop | Medium | Conflict component uses ConfidenceEngine extremes as a disagreement indicator only. RiskEngine does not write to ConfidenceEngine. |
| Smoothing flicker | Medium | `riskSmoothingLength` averaging with `riskTotalRaw` over N bars. Verifier confirms default = 3. |
| Reserved language creeping into dashboard | Medium | Verifier scans dashboard labels for reserved words; exit 1 on violation. |
| ATE v2.1 modification | High | Implementation must not edit `pine/releases/ATE_v2.1.pine`. CI / pre-commit must compare SHA. |
| RDR-003 replaced by verifier | Medium | Implementation plan §14 states explicitly: passing the verifier does NOT replace RDR validation. |
| Pine v6 caching | Low | TradingView caches by script name. Use fresh name when validating. |
| Drift between Pine and Python mirror | Medium | After Pine implementation, verifier must include a parity sub-check that the new Pine produces values that the deterministic Python mirror can reproduce. Document drift. |

## 17. Rollback Plan

Rollback strategy:

1. Stop ATE v2.2 work and freeze the active release file.
2. Revert the development mirror `pine/development/ATE_Current.pine` to the previous commit's content for ATE v2.2 work. If no ATE v2.2 work has been merged, this is a clean no-op.
3. Remove `pine/releases/ATE_v2.2.pine` if it was created.
4. Re-run the ATE v2.1 verifier-only slice from `tools/scripts/verify_ate.py` (which must continue to pass against `pine/releases/ATE_v2.1.pine`).
5. Update `CHANGELOG.md` and `docs/knowledge/ATT_Knowledge_Base.md` to record the rollback with date, reason, and the verifier output that proved ATE v2.1 invariants hold.
6. Open a new RDR if the rollback is for an evidence defect rather than a build defect.

If the verifier extension fails or the verifier returns exit 1 against ATE v2.2, do NOT ship ATE v2.2. Roll back the Pine edits.

### Rollback commitment

No ATE v2.2 release can be marked Stable without:

- ATE v2.1 release file SHA unchanged.
- EDR-001 canonical verifier exit 0.
- RDR-003 (or successor) empirical validation result filed.
